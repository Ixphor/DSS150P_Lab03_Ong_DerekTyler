# Technical Reflection

## Modularity

The pipeline is split by responsibility rather than by pipeline stage. `src/extract/` only copies source snapshots and knows nothing about business rules. `src/transform/` owns staging cleanup, typing, deduplication, curated joins, and quarantine decisions. `src/load/` owns persistence and the UPSERT contract against PostgreSQL. `src/validate/` performs read-only assertions on the curated output. `src/benchmark/` and `src/partition.py` are isolated from production logic and are never invoked by the DAG. `src/cli.py` is a thin composition layer that wires the modules together and resolves the run_id; it contains no transformation logic of its own.

This split matters because it keeps the blast radius of a change small. A change to the curated amount formula only touches `transformer.py`. The Airflow DAG never contains any of these rules. That is what allows the same business logic to be executed locally, inside Docker, and from Airflow without duplicating code, which the lab explicitly requires.

## Idempotency

Every stage is designed so that running it twice for the same logical input produces the same result and does not create duplicate state. Extract writes into `data/raw/run_id=<run_id>/`, keyed by the Airflow run id, so a rerun overwrites the same snapshot. Transform writes into `data/curated/run_id=<run_id>/` and `data/quarantine/run_id=<run_id>/`, and its output is a pure function of the raw snapshot. Load only updates when the incoming `record_hash` differs from the stored one, so a rerun with unchanged business content is a no-op. The hash itself is computed from business columns only (`order_id`, `customer_id`, `product_id`, `quantity`, `status`, `gross_amount`, `net_amount`) and deliberately excludes `pipeline_run_id`, `processed_at_utc`, and `staged_at_utc`, so audit metadata does not make identical rows look different. `load-partition` extends the same contract to `audit.partition_loads` with an UPSERT keyed on `partition_key`, so reloading a month replaces the audit row instead of appending one.

## Storage trade-offs



CSV is the smallest to write and the most portable, but it has no schema, no types, and no compression, so full and filtered reads are slow and status filtering requires reading the whole file. JSON Lines is pipeline-friendly because each line is an independent record, which suits append/stream processing, but it is the largest on disk because keys are repeated on every row, and parsing costs are higher than CSV. Parquet is the smallest on disk because of columnar encoding plus snappy compression, and it is the fastest for filtered reads because only the needed column chunks and row groups are read, which is why the `status = 'DELIVERED'` query is significantly faster than CSV or JSONL. PostgreSQL is not comparable by file size,`pg_total_relation_size` includes table and index storage — but it is the only format that supports concurrent access, transactions, and index-assisted filtering. Adding a B-tree index on `status` would change the PostgreSQL filtered-read result, which is why storage comparisons must be framed as workload-dependent rather than absolute. Partitioning by `order_year` and `order_month` reduces I/O further because a query that filters on the partition key only touches the matching directory; the trade-off is that very high cardinality or low-locality partition keys produce many small files and lose the benefit.

## Orchestration vs business logic

Airflow is used as a scheduler, not as a place to implement transformations. `dags/dss150p_pipeline.py` contains only `BashOperator` tasks that invoke `python -m src.cli <command>` with `PIPELINE_RUN_ID="{{ run_id }}"`. Every business rule — deduplication, typing, joins, amount calculations, the quarantine predicate, the UPSERT conflict target, the record hash definition — lives in `src/` and is called by the CLI. The DAG itself declares schedule (`0 2 * * *`), retries (`retries=2` with a 1-minute delay), execution timeout, a failure callback, parameters (`run_mode`, `year`, `month`), and the dependency chain `extract >> transform >> load >> validate`. The single value that ties all four tasks together is the Airflow run id, which is passed into every task as `PIPELINE_RUN_ID` so that the raw, curated, quarantine, and audit layers all refer to the same logical run. This is why the same logic can be executed by hand, inside the pipeline container, or by the scheduler without divergence, and why a failure at extract correctly blocks transform, load, and validate rather than producing partial state.
